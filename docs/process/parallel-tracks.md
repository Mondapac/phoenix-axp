# مسیرهای کاری موازی

**تأیید:** علی (cto) | **ارزیابی فرایند:** جواد (scrum-master) | **تاریخ:** ۲۰۲۶-۱۰-۲۶ | **مبنا:** [قوانین کار پروژه](../../CLAUDE.md) قاعدهٔ ۱۵، ADR-0013، Mondapac `parallel-tracks.md`

**تصمیم صاحب پروژه (۲۰۲۶-۱۰-۲۶):** ساخت Phoenix AXP در حداکثر چهار مسیر موازی پیش می‌رود. هر مسیر یک session، یک شاخه و یک worktree یا clone جدا دارد. Claude شاخه را push می‌کند و PR می‌سازد؛ فقط صاحب پروژه merge می‌کند.

## هدف
چند session بدون برخورد کار کنند: هیچ session شاخهٔ دیگری را عوض نکند، دو session یک فایل را هم‌زمان تغییر ندهند، و صاحب پروژه همیشه بداند هر مسیر کجاست و چه چیزی منتظر اوست.

## مسیرها و محدودهٔ نوشتن

| مسیر | کار | نقش‌ها | محدودهٔ نوشتن |
|---|---|---|---|
| `backend` | هسته، `platform/`، ماژول‌های هسته، ابزار و CI | حسین، محمد، مجتبی، کاظم | `apps/api/` (به‌جز ماژول‌های مسیر `process`)، `prisma/`، `packages/shared-kernel/`، `config/`، `scripts/`، `test/`، `docs/design/{domain,data}/`، `docs/reviews/` |
| `process` | فرم، process، Flowable و objects | حسین، محمد | `apps/api/src/modules/{forms,process,objects}/`، `prisma/schema/{forms,process,objects}.prisma` |
| `frontend` | پنل‌ها و پورتال | مهدی، رضا، جعفر | `apps/admin/`، `apps/studio/`، `apps/portal/`، `packages/ui/`، `packages/panel-server/`، `docs/design/flows/` |
| `product` | یک قدم جلوتر از کد: بستهٔ مرور فاز بعد، برگه‌ها، قابلیت‌ها، کنترل پروژه | هادی، علی، جواد | `docs/phases/`، `docs/modules/<ماژول>/` تا تأیید G1، `docs/features/`، `docs/project/` (فقط جواد) |

- نقش‌های بازبین (ساجد، حسن، باقر، مجتبی، علی) در هر مسیری که لازم باشد فراخوانده می‌شوند و فقط می‌خوانند.
- خواندن همه‌جا آزاد است.
- هر مسیری که در جدول نیست، **فایل مشترک** است.
- فایل هر ADR متعلق به مسیری است که شماره‌اش را روی تابلو رزرو کرده است.
- پوشهٔ هر ماژول با ثبت G1 از مسیر `product` به مسیر سازنده (`backend`، `process` یا `frontend`) تحویل می‌شود و این روی تابلو ثبت می‌شود.

## فایل‌های مشترک
- `CLAUDE.md`، `README.md`، `PLAYBOOK-fa.md`، `TEAM-PLAYBOOK-fa.md`، `.claude/`
- `docs/modules/README.md`، `docs/modules/_template/`، `docs/process/` (از جمله تابلو)
- شماره‌گذاری `docs/adr/` و `docs/adr/README.md`، `docs/phases/`
- `package.json` ریشه، `pnpm-lock.yaml`، `pnpm-workspace.yaml`، `tsconfig*.json`، `eslint.config.mjs`، `prisma.config.ts` و فایل‌های نقطه‌دار ریشه
- `.github/workflows/`، `docker-compose.yml`، `.env.example`
- ترتیب migrationها در `prisma/`

**قواعد:**
1. **PR کوچک و جدا.** تغییر فایل مشترک در PR خودش می‌آید. دو استثنا، هر دو با ثبت روی تابلو: ردیف ماژول در `docs/modules/README.md` همراه ثبت دروازه در برگه؛ و `CLAUDE.md` همراه ADRی که قاعدهٔ سختی را عوض می‌کند.
2. **اول روی تابلو.** پیش از شروع، فایل به نام مسیر در بخش «فایل‌های مشترک در دست» ثبت می‌شود. تا merge آن PR، مسیر دیگری آن را تغییر نمی‌دهد.
3. **شمارهٔ ADR** پیش از نوشتن روی تابلو رزرو می‌شود.
4. **lockfile و وابستگی:** `pnpm-lock.yaml` دستی ادغام نمی‌شود؛ هنگام تعارض `pnpm install` اجرا و نتیجه commit می‌شود. هر وابستگی تازه یک PR جدا با ذکر مجوز (ADR-0009).
5. **migration:** در speed mode قاعدهٔ «یک PR migration باز» برداشته شده است؛ پیش از merge شاخه با `main` به‌روز و در صورت نیاز migration دوباره ساخته می‌شود. migrationِ merge‌شده ویرایش نمی‌شود. امضای مجتبی لازم است.

## تابلو
تابلو فایل [`docs/process/tracks.md`](tracks.md) در همین مخزن است و تنها حافظهٔ مشترک sessionهاست. نسخهٔ معتبر همان است که روی `origin/main` است؛ به‌روزرسانی‌ها مثل هر تغییر دیگری با PR می‌آیند. محتوای آن:
- شمارهٔ `revision`، وضعیت فاز و `main`
- ردیف هر مسیر: worktree، شاخه، PR باز، کار فعلی، منتظرِ چه چیزی
- فایل‌های مشترک در دست
- شماره‌های ADR رزروشده
- درخواست‌های بین مسیرها
- صف اقدام صاحب پروژه، مرتب و با تاریخ بازشدن

## جریان کار هر session
```
شروع → fetch و خواندن تابلو → بررسی worktree، شاخه و مرور فاز
     → کار در محدودهٔ مسیر (یک قابلیت = یک شاخه = یک PR)
     → به‌روز کردن شاخه با main → pnpm verify → push → PR
     → به‌روزرسانی ردیف تابلو (روزی یک بار) → گزارش فارسی به صاحب پروژه
صاحب پروژه: مرور PR → merge به ترتیب تابلو
```
جزئیات: skill `phoenix-track-session` و `phoenix-repo-doc-change`.

| گام | انجام‌دهنده | پاسخ‌گو | مشورت | مطلع |
|---|---|---|---|---|
| تعریف یا تغییر مسیرها | مسیر `product` | صاحب پروژه | علی، جواد | همهٔ مسیرها (تابلو) |
| کار در مسیر، push و PR | session همان مسیر | نقش مسئول برش | نقش‌های بازبین | صاحب پروژه |
| تغییر فایل مشترک | مسیری که روی تابلو ثبت کرده | علی | مسیرهای مصرف‌کننده | تابلو |
| merge | صاحب پروژه | صاحب پروژه | باقر (QC) | تابلو |
| ارزیابی سلامت این فرایند | جواد | جواد | صاحب پروژه | علی |

## حالت‌های خاص
| وضعیت | چه باید کرد |
|---|---|
| session در worktree مسیر دیگری است | آنجا ننویس و شاخه عوض نکن؛ به صاحب پروژه بگو. |
| دو مسیر یک فایل مشترک را لازم دارند | مسیری که زودتر ثبت کرده جلو می‌رود؛ دیگری بعد از merge شاخه‌اش را به‌روز می‌کند. اختلاف با علی. |
| شمارهٔ ADR تکراری شد | ADRی که دیرتر merge می‌شود شمارهٔ آزاد بعدی را می‌گیرد. |
| شاخهٔ push‌شده از `main` عقب افتاد | `main` را در شاخه merge کن؛ تاریخچهٔ push‌شده بازنویسی نمی‌شود. |
| تعارض روی تابلو | PR دیرتر ردیف‌های دیگران را نگه می‌دارد و `revision` بعدی را می‌گیرد. |
| کاری مال مسیر دیگر است | در «درخواست‌های بین مسیرها» ثبت کن؛ خودت انجام نده. |
| PoC فاز ۰ | کد PoC در شاخهٔ جدا اجرا می‌شود و merge نمی‌شود؛ فقط گزارش در `docs/reviews/` با PR مستندات می‌آید. |
