# بستهٔ مرور فاز ۲: فرم، BPM و Objects

**وضعیت:** D1 تا D8 قطعی (۲۰۲۶-۱۰-۲۷)؛ D9 در مرور؛ سپس تأیید نهایی صاحب پروژه | **تاریخ:** ۲۰۲۶-۱۰-۲۷ | **دستور شروع:** صاحب پروژه، ۲۰۲۶-۱۰-۲۷ («فاز 2 رو شروع کن») | **برش:** 1.11 (مسیر `product`) | **قانون:** هیچ برشی از این فاز پیش از «تصمیم نهایی» صاحب پروژه (بخش ۷) ساخته نمی‌شود (`CLAUDE.md` قاعدهٔ ۱۳، ADR-0013).

**منابع:** `PLAYBOOK-fa.md` (فاز ۲)، ADR-0004، ADR-0005، ADR-0006، ADR-0007، ADR-0020؛ `docs/reviews/poc-3-flowable-bridge.md` و `poc-4-rtl-portal.md`؛ بخش ۳ سند «کاربران و روش‌های ثبت فرم» (قطعی ۲۰۲۶-۱۰-۲۷)؛ مرور فاز ۱، بخش ۳ (دو پاسخ از پیش گرفته‌شده برای این مرور).

## ۱. هدف فاز
سه ماژول سطح A که هر خدمت سازمانی روی آن‌ها ساخته می‌شود:
- **forms:** فرم‌ساز نسخه‌دار (JSON Schema و UI Schema، revision منتشرشدهٔ تغییرناپذیر)، سیاست ثبت برای هر فرم (عمومی بدون ورود، کاربر واردشده، کارکنان یا نقش‌های مشخص، ثبت «از طرف»)، کد رهگیری، CAPTCHA خودمیزبان، صندوق فرم.
- **process:** ماژول process با Flowable به‌صورت سرویس جدا، از طریق outbox و inbox، با همهٔ تغییرهای طراحی PoC ۳؛ مدل‌ساز bpmn-js در studio؛ Task Inbox («کارهای من»)؛ تایمر، escalation و DMN.
- **objects:** مدل‌سازی دادهٔ low-code به سبک Liferay Objects، با API تولیدی که هر عملیاتش یک use case با `access` است و مجوز سطح رکورد دارد (ADR-0017).

**معیار:** در یک وزارت نمونه، کارمند مدیریت فرم در studio فرم «درخواست ملاقات» را می‌سازد و منتشر می‌کند و آن را به فرایند «بررسی ← تأیید ← تعیین وقت» با مهلت و escalation وصل می‌کند. شهروند بدون ورود فرم را با CAPTCHA ثبت می‌کند و کد رهگیری می‌گیرد. کارمند سایت فارس کار را در «کارهای من» می‌بیند و انجام می‌دهد؛ کارمند سایت دیگر آن را نمی‌بیند. اگر مهلت بگذرد، کار به مدیر می‌رسد. یک Object «شکایت» با فیلدهایش تعریف می‌شود و API آن فقط به دارندگان مجوز پاسخ می‌دهد. همه در audit ثبت می‌شود، روی دو مستأجر آزمایشی با زبان، تقویم و منطقهٔ زمانی متفاوت.

**وابستگی به فاز ۱:** برش‌های 1.6 (نقش و اعطا)، 1.8 (`subject-keys`، `rate-limit`، `mail`) و 1.10 (پوستهٔ studio) هنوز در ترد فاز ۱ ساخته می‌شوند. 2.1، 2.2 و 2.4 به آن‌ها وابسته نیستند؛ 2.3 و 2.5 به 1.6 و 1.8 و برش‌های frontend به 1.10 وابسته‌اند (تصمیم D1).

**مسیرهای فعال (حداکثر چهار):** `process`، `backend`، `frontend`، `product`.

**تصمیم‌های فنی تیم (نه پرسش صاحب پروژه):** CAPTCHA خودمیزبان از نوع proof-of-work بدون تصویر (مثل ALTCHA، MIT)، با بررسی مجوز در PR جدا؛ Ajv (MIT) برای اعتبارسنجی؛ JSON Forms (MIT) و bpmn-js (مجوز bpmn.io با watermark، بررسی موردی علی طبق ADR-0009)؛ متغیرهای فرایند فقط شناسه، بدون دادهٔ شخصی (ADR-0005).

## ۶. معیار خروج از فاز ۲
- سناریوی بخش ۱ روی دو مستأجر آزمایشی سرتاسر کار کند.
- هر ماتریس خطای PoC ۳ (قطعی Flowable، worker و هسته) روی ماژول process تکرار و سبز شود.
- آزمون «مستأجر اشتباه» برای هر کوئری adapter Flowable وجود داشته باشد و سبز باشد.
- هیچ use case تولیدی Objects بی‌قاعدهٔ `access` نباشد (CI).
- فیلد پنهان برای یک نقش در هیچ مسیری (صفحه، REST، GraphQL، خروجی، جست‌وجو) دیده نشود و فیلد فقط‌مشاهده ویرایش نشود (آزمون روی دو مستأجر).
- حسن پل Flowable، ثبت ناشناس و دادهٔ شخصی فرم و مجوز سطح رکورد Objects را بازبینی کرده و یافتهٔ Critical یا High باز نباشد.
- `pnpm verify` و CI روی main سبز باشد.
- بستهٔ مرور فاز ۳ آماده باشد.
- باقر (QC) بررسی کرده و صاحب پروژه بستن فاز را تأیید کرده باشد.
